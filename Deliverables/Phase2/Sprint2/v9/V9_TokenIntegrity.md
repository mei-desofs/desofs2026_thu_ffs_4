## V9.1 Token source and integrity

| Section ID | Section Name               | Req ID | Description                                                                                                                                                                                                                                                                                                                                                                                       | Level | Status    | Observations                                                                                                                                                     |
| ---------- | -------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V9.1       | Token source and integrity | V9.1.1 | Verify that self-contained tokens are validated using their digital signature or MAC to protect against tampering before accepting the token's contents.                                                                                                                                                                                                                                          | 1     | Completed | The backend validates JWT signatures with `jsonwebtoken.verify` before reading claims, and authenticated requests are also bound to server-side session records. |
| V9.1       | Token source and integrity | V9.1.2 | Verify that only algorithms on an allowlist can be used to create and verify self-contained tokens, for a given context. The allowlist must include the permitted algorithms, ideally only either symmetric or asymmetric algorithms, and must not include the 'None' algorithm. If both symmetric and asymmetric must be supported, additional controls will be needed to prevent key confusion. | 1     | Completed | Session tokens are restricted to `HS256` only. The `none` algorithm is not accepted.                                                                             |
| V9.1       | Token source and integrity | V9.1.3 | Verify that key material that is used to validate self-contained tokens is from trusted pre-configured sources for the token issuer, preventing attackers from specifying untrusted sources and keys. For JWTs and other JWS structures, headers such as 'jku', 'x5u', and 'jwk' must be validated against an allowlist of trusted sources.                                                       | 1     | Completed | The backend uses a preconfigured shared secret from environment configuration and rejects tokens that advertise `jku`, `x5u`, or `jwk` headers.                  |

## V9.2 Token content

| Section ID | Section Name  | Req ID | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Level | Status    | Observations                                                                                                                     |
| ---------- | ------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- | --------- | -------------------------------------------------------------------------------------------------------------------------------- |
| V9.2       | Token content | V9.2.1 | Verify that, if a validity time span is present in the token data, the token and its content are accepted only if the verification time is within this validity time span. For example, for JWTs, the claims 'nbf' and 'exp' must be verified.                                                                                                                                                                                                                 | 1     | Completed | Tokens are signed with `exp` and verified with `jsonwebtoken.verify`, which enforces `exp` and `nbf` checks.                     |
| V9.2       | Token content | V9.2.2 | Verify that the service receiving a token validates the token to be the correct type and is meant for the intended purpose before accepting the token's contents. For example, only access tokens can be accepted for authorization decisions and only ID Tokens can be used for proving user authentication.                                                                                                                                                  | 2     | Completed | Session JWTs carry a `tokenType=access` claim and are only accepted for authorization/session checks. No ID token flow exists.   |
| V9.2       | Token content | V9.2.3 | Verify that the service only accepts tokens which are intended for use with that service (audience). For JWTs, this can be achieved by validating the 'aud' claim against an allowlist defined in the service.                                                                                                                                                                                                                                                 | 2     | Completed | Session tokens are issued with and verified against a single explicit audience: `cantinasapp-backend-api`.                       |
| V9.2       | Token content | V9.2.4 | Verify that, if a token issuer uses the same private key for issuing tokens to different audiences, the issued tokens contain an audience restriction that uniquely identifies the intended audiences. This will prevent a token from being reused with an unintended audience. If the audience identifier is dynamically provisioned, the token issuer must validate these audiences in order to make sure that they do not result in audience impersonation. | 2     | Completed | The issuer includes a unique audience restriction for the backend API, so the token cannot be reused for an unintended audience. |

## Implementation Notes

- Token policy constants live in `CantinasApp/Backend/src/utils/jwtPolicy.ts`.
- JWT issuance and verification are centralized in `CantinasApp/Backend/src/Service/SessionService.ts`.
- Authentication middleware delegates to the session service for signed-token verification and server-side session checks.
- The token format remains JWT-based, but the backend now enforces algorithm, issuer, audience, token type, and header-source restrictions.
